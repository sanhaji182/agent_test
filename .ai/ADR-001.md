# ADR-001 — Canonical Execution Orchestrator

**Status:** Accepted  
**Date:** 2026-07-27  
**Deciders:** Engineering owner  
**Supersedes:** None

## Context

The system has 5 diverging execution paths, each with different state transitions, retry logic, runner selection, persistence, and error behavior:

| Path | Trigger | Runner | State flow | Retries | Persistence |
|---|---|---|---|---|---|
| Web API (`handleCreateRun`) | `POST /api/v1/runs` | `executeRealRun` | idle→analyzing→plan_generated→writing_tests→running→fixing→done/failed | Yes (3x) | Full |
| GitHub Webhook | `POST /api/v1/webhooks/github` | `executeRealRun` | idle→analyzing→...→done/failed | Yes (3x) | Full |
| Schedule (test list) | `ProcessDueSchedules` / `handleRunNow` | `startTestListRuns`→`startTestCaseRun`→`executeApprovedTestCaseRun` | idle→writing_tests→running→done/failed | No | Full |
| Schedule (non-list) | `ProcessDueSchedules` / `handleRunNow` | `executeRealRun` | idle→analyzing→...→done/failed | Yes (3x) | Full |
| MCP / Agent | MCP tool `run_tests` | `executeRealRun` (via agent loop) | idle→analyzing→...→done/failed | Yes (3x) | Full |

All five produce `agent.TestRun` rows in the same `test_runs` table, but:
- The approved-case path has no fix loop (synthetic step-walk for non-Docker, real execution via Docker)
- The webhook path creates a goroutine inside a callback with no server-level error boundary
- The schedule path had the bug (TODO-008) where non-list runs were never triggered
- The MCP path runs in-process via the Agent loop (`internal/agent/agent.go`)

Furthermore, `internal/agent/agent.go` contains a separate complete executor (`Agent.Execute`) with its own state machine, plan generation, test file generation, runner dispatch, fix loop, and result persistence. This duplicates significant logic from `executeRealRun` in `server.go`.

## Decision

**Adopt a single canonical orchestrator:** Extract a unified `Executor` type in the `internal/agent` package that:
1. Accepts a `RunRequest` (mode, project path, requirements, test type, etc.)
2. Creates the run via the store
3. Runs the complete lifecycle: analyze → plan → write → run → fix (optional) → done/failed
4. Emits events for SSE consumption
5. Returns the terminal `agent.TestRun`

All 5 entry points become thin adapters that construct a `RunRequest` and call `executor.Execute(request)`.

### Key design constraints
- **No change to database schema** — `test_runs` table unchanged
- **No change to HTTP contract** — route signatures, request/response bodies unchanged
- **No change to SSE event format** — `events.Store.Emit` signature unchanged
- **Backward compatible** — existing runs, schedules, webhooks continue to work

### What gets unified
- Single state transition table (currently duplicated across `agent.go:181-340` and `server.go:1856-1998`)
- Single fix loop (3-attempt retry, currently only in `agent.go` and `executeRealRun`)
- Single event emission for run lifecycle milestones
- Single error boundary with consistent logging

### What stays separate
- Entry-point-specific pre-processing (webhook HMAC, MCP parameter mapping, schedule project resolution)
- Mode-specific execution (`approved_case` dispatches to `executeApprovedTestCaseRun`; `simple` is the default `executeRealRun` path)

## Consequences

### Positive
- **Correctness:** All paths get the fix loop. All paths get proper error states.
- **Maintainability:** Change the executor once and all paths benefit.
- **Testability:** Single executor can be tested in isolation.
- **Unblocks:** TODO-007 (consolidation), TODO-008 (schedule fix — done via narrow patch, but proper fix is here), TODO-010 (synthetic success paths inherit real execution).

### Negative
- **Risk:** Extracting the executor touches the most heavily-used code path in the project (1700+ lines of `executeRealRun` and `Agent.Execute`). Must be done incrementally.
- **Migration effort:** Existing goroutine-based callers (`go s.executeRealRun(run)`) become `go s.executor.Execute(run)`. Each call site needs verification.

### Neutral
- The approved-case non-Docker path with its synthetic step-walk will still exist post-consolidation; this ADR does not change the decision to have it (that's ADR-002's domain).

## Alternatives considered

1. **Status quo** — Rejected. Five paths that diverged organically will continue to diverge as new features are added.
2. **Route through a queue (Asynq)** — Rejected. The existing Asynq integration is lightly used; adding a queue dependency for all paths adds complexity and latency for no current gain.
3. **Extract to `internal/orchestrator` package** — Rejected. Moving to a new package changes the public API surface. The existing `internal/agent` package already owns the `Agent.Execute` path; unifying there minimizes changes.
