# ADR-004 — Scheduling and Concurrency

**Status:** Accepted
**Date:** 2026-07-27
**Deciders:** Engineering owner
**Supersedes:** None

## Context

The scheduler currently runs as a single in-process goroutine (`cmd/server/main.go:runScheduler`) that polls every 60 seconds:

```go
func runScheduler(ctx context.Context, srv *api.Server) {
    ticker := time.NewTicker(60 * time.Second)
    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            srv.ProcessDueSchedules(context.Background(), time.Now())
        }
    }
}
```

Issues:
1. **No claiming/leasing:** `ProcessDueSchedules` calls `s.schedules.GetDue(now)` then iterates. If two instances run simultaneously, both will process the same due schedule → duplicate runs.
2. **No horizontal scaling:** Single goroutine, single instance. Adding instances doesn't distribute load.
3. **No failure recovery:** If the scheduler goroutine panics (it has a recover, but `ProcessDueSchedules` could fail), no mechanism retries missed schedules.
4. **Resolution is 60 seconds:** Cron expressions with sub-minute granularity (e.g., `*/30 * * * * *`) aren't supported because `GetDue(now)` is only called every 60s.

Additionally, `TODO-017` notes that `schedule/store.go:245-269` uses separate select + update for due schedules — no atomic claim to prevent duplicate processing across overlapping workers.

The Asynq queue is deployed (Redis is a Compose service) and the Asynq dependency is in `go.mod` (`github.com/hibiken/asynq v0.25.1`), but it is not used for schedule dispatch. It is currently only wired for report generation (`internal/reporter/`).

## Decision

**Use Asynq for schedule dispatch, keep the goroutine for scheduling only.**

### Strategy

1. **Scheduler goroutine** (runs in-process, lightweight):
   - Checks `GetDue(now)` on its tick
   - For each due schedule, enqueues a `ScheduleTask` into Asynq (Redis)
   - Does NOT create runs directly

2. **Asynq worker** (runs in-process using existing Redis, or standalone):
   - Picks up `ScheduleTask` from Redis queue
   - Atomically claims the schedule (UPDATE with `WHERE next_run_at = $old_value`) to prevent duplicates
   - Creates the run via the canonical executor (ADR-001)
   - On success: updates `next_run_at`
   - On failure: retries with exponential backoff (Asynq built-in)

3. **Multi-instance safety:**
   - Atomic schedule claiming in the worker prevents duplicate runs
   - Asynq's Redis-based task distribution works across instances
   - Each instance runs both the scheduler goroutine and an Asynq worker

### Migration path
1. Add `EnqueueSchedule(scheduleID string)` method
2. Add Asynq task handler that calls canonical executor
3. Wire into existing Redis connection from `main.go`
4. Keep `ProcessDueSchedules` as the adapter between scheduler tick → Asynq enqueue

## Consequences

### Positive
- **No duplicate runs:** Atomic claim prevents the TODO-017 race condition.
- **Retry with backoff:** Failed schedule runs retry automatically.
- **Multi-instance ready:** Two instances don't double-process schedules.
- **Uses existing infrastructure:** Redis is already deployed; Asynq is already a dependency.

### Negative
- **Increased complexity:** One more moving part in the execution pipeline.
- **Redis becomes required for scheduling:** Currently the scheduler works without Redis. Post-ADR-004, schedules require Redis.

### Neutral
- The 60-second polling resolution remains unchanged for now. Sub-minute scheduling can be added by reducing the tick interval or adding cron-awareness to `GetDue`.

## Alternatives considered

1. **PostgreSQL advisory locks** — Rejected. Would require a DB connection per scheduler instance and doesn't provide retry/backoff semantics.
2. **Leader election with single scheduler instance** — Rejected. Adds complexity without solving the retry problem. Multi-instance is better served by a shared queue.
3. **Remove in-process scheduling entirely, use external cron** — Rejected. The in-process scheduler is simple, works in development without external dependencies, and the combined "tick + enqueue" pattern keeps the entry point unified.
4. **Status quo (single goroutine, no claims)** — Rejected. Already causing real bugs (TODO-008, TODO-017).
