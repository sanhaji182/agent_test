# ADR-002 — Browser Backend Selection

**Status:** Accepted  
**Date:** 2026-07-27  
**Deciders:** Engineering owner  
**Supersedes:** None

## Context

The system has three browser execution backends, only one of which is fully functional:

| Backend | Code location | Status | Used by |
|---|---|---|---|
| Playwright (direct) | `internal/agent/playwright_runner.go` | **Working** — spawns local Playwright process with self-healing | `Agent.Execute` (non-Steel path) |
| Playwright (Docker) | `internal/runner/docker.go` | **Working** — runs Playwright in Docker container | `executeApprovedTestCaseWithDocker` |
| Steel Browser | `internal/steel/` | **Partial** — Steel client code exists but no runner integration found | Unclear — referenced in config/env but no active dispatch path |

The runner dispatch is currently implicit:
- `Agent.Execute` checks `run.TestType == "api"` → `APIRunner` (mock) else uses the `PlaywrightRunner` set at `Agent` construction
- `executeRealRun` always constructs a `PlaywrightRunner` directly
- `executeApprovedTestCaseRun` dispatches to Docker path only when `GOTEST_APPROVED_CASE_RUNNER=docker`

There is no runner factory, no runner registry, and no unified error/reporting contract. Each runner produces a `RunResult`, but the interpretation of `Passed`/`Failed` differs:
- Playwright (direct): Was hardcoded `Passed: 1, Failed: 0` regardless of outcomes (fixed in TODO-010 to `Passed: 0`)
- API runner: Was marking all files passed in mock loop (fixed in TODO-010 to zero)
- Docker: Returns actual Playwright results from container
- Steel: No runner integration found

## Decision

**Standardize on Playwright as the canonical browser backend** with a unified runner interface and explicit runner selection:

### Runner interface (already implicit in code)
```go
type Runner interface {
    Run(ctx context.Context, testFiles []TestFile, projectURL string) (*RunResult, error)
}
```

### Runner selection strategy
1. All browser tests run via Playwright — either direct (development, isolated environments) or Docker (production, sandboxed).
2. Steel Browser is deprecated as a separate backend. The Steel API client code is kept but marked as inactive until a concrete integration need is identified.
3. A `NewRunner(cfg)` factory selects the implementation based on `GOTEST_RUNNER` env var:
   - `"docker"` → `DockerRunner` (current `internal/runner/docker.go`)
   - `"playwright"` / empty → `PlaywrightRunner` (current `internal/agent/playwright_runner.go`)
4. Docker becomes the **default in production** (`APP_ENV=production` with no explicit `GOTEST_RUNNER`).

### What the runner is NOT responsible for
- Plan generation, code analysis, test file generation → executor
- Event emission → executor via `events.Store`
- State transitions → executor
- Video/storage management → executor (reads `result.VideoPath`)

## Consequences

### Positive
- **Simplification:** Two backends instead of three; one decision instead of implicit dispatch.
- **Sandboxing:** Docker runner provides process isolation for untrusted test code.
- **Honest results:** `Passed`/`Failed` counts now mean what they say (TODO-010 fixed the synthetic success).
- **Testability:** Single `Runner` interface means mocks work for executor tests.

### Negative
- **Steel Browser deprecation:** Removes a potential vector for scalability (Steel's session management). If multi-tenant browser execution becomes a requirement, the Steel client may need resurrection.
- **Docker requirement in production:** Adds Docker runtime dependency for production deployments. Direct Playwright is available as a fallback.

### Neutral
- The approved-case path in non-Docker mode continues to produce simulated results (`StateSimulated`) — this ADR does not change that behavior (it's an executor concern, not a runner concern).

## Alternatives considered

1. **Embrace Steel as the canonical backend** — Rejected. No active runner integration exists; the Steel client code has no dispatch path. Adopting it now would require building a new runner, testing, and deployment changes for uncertain benefit.
2. **Keep all three backends** — Rejected. The implicit dispatch and incomplete Steel integration create confusion and maintenance burden.
3. **Remove Docker, keep only direct Playwright** — Rejected. Docker provides essential sandboxing for production execution of untrusted LLM-generated test code.
