# ADR-003 — Operational State Durability

**Status:** Accepted  
**Date:** 2026-07-27  
**Deciders:** Engineering owner  
**Supersedes:** None

## Context

The server currently uses 7 memory-only stores that lose all data on restart:

| Store | Type | Data lost on restart | Impact |
|---|---|---|---|
| `events.Store` | In-memory map | Event history (SSE replay, run logs) | Dashboard shows gaps on refresh |
| `recordings.Store` | In-memory map | Screenshot/step metadata | Run detail loses recording timeline |
| `visuals.Store` | In-memory map | Baseline vs. current comparisons | Lost comparison data |
| `releases.Store` | In-memory map | Release tracking | All release history gone |
| `notifs.Store` | In-memory map | Notification history | Alert timeline cleared |
| `reviews.Store` | In-memory map | Review approvals | Audit trail lost |
| `suites.Store` | In-memory map | Suite configurations | Suite definitions lost |

Persistent stores exist for: test_runs (RunStore), projects, schedules, plans/cases/lists/proposals, settings.

Additionally:
- `sidecar/main.py` stores jobs in a Python `dict` — sidecar restart loses all in-flight LangGraph jobs
- Asynq queue uses Redis — durable but currently unused (no active workers enqueueing)

## Decision

**Phase the durability rollout based on criticality:**

### Phase 1 — Restart-safe (now)
For stores where data loss on restart has immediate user-visible impact:
- **events.Store** → PostgreSQL `run_events` table (run_id, event_type, state, message, metadata JSONB, created_at). Needed for SSE replay and run log persistence. Most impactful — dashboard is unusable after restart without this.
- **Sidecar jobs** → Redis (already available). Store job state in Redis with TTL. Sidecar restart scans Redis to recover in-flight jobs.

### Phase 2 — Recovery-important (next)
For stores where data loss matters for audit/accuracy but not immediate operation:
- **releases.Store** → PostgreSQL `releases` table
- **reviews.Store** → PostgreSQL `reviews` table
- **suites.Store** → PostgreSQL `suites` table

### Phase 3 — Bounded memory (acceptable risk)
For stores where data is inherently ephemeral:
- **recordings.Store** — Keep in memory with explicit size cap. Recordings are tied to run lifecycle; once a run is terminal, recordings can be garbage collected.
- **visuals.Store** — Keep in memory with size cap. Comparison data is transient.
- **notifs.Store** — Keep in memory with size cap and ring-buffer semantics (keep last 100).

### What stays ephemeral
- In-flight SSE connections
- Active Playwright browser sessions
- Goroutine run contexts (canceled on restart, runs resume as "failed" on next startup check)

## Consequences

### Positive
- **Restart resilience:** Server restart no longer destroys event history, release data, or sidecar jobs.
- **Memory bounds:** Explicit caps on ephemeral stores prevent unbounded memory growth.
- **Audit trail:** Review approvals and release states survive restarts.

### Negative
- **Migration effort:** 3-4 new tables and migrations for Phase 1-2.
- **Write amplification:** Every event emission becomes a DB write (currently in-memory). Can be mitigated with batching or async writes.
- **SSE replay complexity:** Reading events from DB for replay on SSE connect adds query latency.

### Neutral
- PostgreSQL is already the persistence layer for all other data — adding tables is incremental, not architectural.

## Alternatives considered

1. **Full PostgreSQL for all stores** — Rejected. Recordings and visuals are high-churn, transient data that would cause unnecessary DB write load. Explicit memory caps with documented ephemerality are sufficient.
2. **Redis for all stores** — Rejected. Adds operational dependency for data types that don't need TTL semantics. PostgreSQL is already required; Redis is optional (used only by Asynq).
3. **Status quo (all memory)** — Rejected. This is the root cause of TODO-011 and makes the system unsuitable for anything beyond development.
