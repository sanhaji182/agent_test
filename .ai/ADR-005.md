# ADR-005 — Authentication and Authorization Model

**Status:** Accepted  
**Date:** 2026-07-27  
**Deciders:** Engineering owner  
**Supersedes:** None

## Context

Authentication in the system currently uses a single `API_KEY` environment variable:

```go
// internal/api/server.go (apiKeyAuth middleware)
func (s *Server) apiKeyAuth(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if s.cfg.APIKey == "" { return next.ServeHTTP(w, r) } // bypass if no key set
        key := r.Header.Get("X-Api-Key")
        if key != s.cfg.APIKey { http.Error(w, "unauthorized", 401); return }
        next.ServeHTTP(w, r)
    })
}
```

### Problems
1. **No browser-safe auth:** The dashboard (`frontend/src/lib/api.ts`) sends no `X-Api-Key` header, and `EventSource` (SSE) cannot set custom headers. This means the dashboard is either unauthenticated or completely broken in production.
2. **Shared secret everywhere:** `API_KEY` is used for:
   - HTTP API authentication (end users, dashboard)
   - Sidecar authentication (`GOTEST_API_KEY` passed to sidecar, which sends it back to backend)
   - GitHub webhook fallback (now separated — TODO-004)
3. **No user/role model:** One key grants full access. No concept of read-only, admin, or scoped access.
4. **Credential exfiltration path:** Settings can change `llm_base_url`, and execution sends the stored API key as Bearer auth to that URL. A caller who can set a global setting can redirect LLM calls to their own server and capture the key (TODO-006).

## Decision

**Adopt a three-tier auth model phased by priority:**

### Phase 1 — Dashboard token (cookie-based)
**Why first:** Unblocks TODO-005 (dashboard auth), the highest-impact auth gap.

1. Add `POST /api/v1/auth/login` endpoint that accepts `{ "api_key": "..." }` and returns a JWT as an httpOnly cookie.
2. Auth middleware checks JWT cookie first; falls back to `X-Api-Key` header for API clients.
3. JWT has short lifespan (1 hour) with refresh (24 hours).
4. SSE endpoint checks JWT via query parameter (`?token=...`) since `EventSource` can't send cookies.

This makes the dashboard work in production with authentication while preserving backward compatibility for CLI/API clients using `X-Api-Key`.

### Phase 2 — Scoped tokens
**Why second:** Enables safe CI/CD integration and multi-team use.

1. Settings API (`POST /api/v1/settings`) adds a JWT-based scope system — settings mutations require `admin` scope.
2. CI/CD tokens can be generated with `run:create` scope only (can create runs, cannot change settings or view keys).
3. Frontend dashboard tokens get `dashboard` scope (read runs, view status, trigger reruns).

This closes TODO-006 by requiring admin scope to change `llm_base_url` or any LLM provider settings.

### Phase 3 — Sidecar auth (mutual TLS or service token)
**Why last:** Sidecar is the hardest boundary and currently has no auth at all (TODO-003).

1. Generate a service-specific JWT with short TTL for sidecar ↔ backend communication.
2. Backend validates service token separately from user tokens.
3. Alternatively: put sidecar behind internal Docker network only (remove public port publication) and use shared network authentication.

### What does NOT change
- `API_KEY` remains the root credential for initial setup and backward compatibility
- `X-Api-Key` header continues to work for API clients
- `APP_ENV=development` with empty `API_KEY` continues to bypass auth

## Consequences

### Positive
- **Dashboard works in production:** JWT cookie solves the `EventSource` header problem.
- **Credential exfiltration prevented:** Scoped tokens mean LLM base URL changes require admin scope.
- **Sidecar isolation:** Three-tier model prevents confused deputy (sidecar has its own credential type).
- **Incremental:** Each phase is independently deployable.

### Negative
- **JWT secret management:** Adds a new secret (`JWT_SECRET`) that must be generated and rotated.
- **Cookie complexity:** HttpOnly cookies add CSRF considerations (mitigated by SameSite=Strict).
- **Migration effort:** All auth middleware paths change; regression testing required.

### Neutral
- Existing `X-Api-Key` clients are unaffected — the middleware tries cookie first, then falls back to header.

## Alternatives considered

1. **OAuth2/OIDC provider integration** — Rejected for now. Adds external dependency (Keycloak, Auth0) that many self-hosted users won't have. Can be added later as an alternative auth method.
2. **Session-based auth (server-side sessions)** — Rejected. Adds server state; JWT is stateless and simpler for the multi-instance case (ADR-004).
3. **mTLS everywhere** — Rejected. Overkill for a self-hosted tool. TLS termination at the reverse proxy is the standard deployment pattern.
4. **Status quo** — Rejected. Dashboard cannot authenticate; sidecar has no auth boundary; credential exfiltration possible.
