**Scope:** Design and code-organization principles derived from existing repository patterns and audit recommendations

## Code-Evidenced Principles

These principles reflect patterns already present in the tracked source. They are descriptive (this is how the codebase works today) and prescriptive (maintain this pattern in future changes).

### 1. Package-per-domain

**Evidence:** `internal/agent`, `internal/project`, `internal/schedule`, `internal/db`, `internal/events`, `internal/notify`, `internal/release`, `internal/workflow`, `internal/planning` (reconstructed).  
**Rule:** Each business domain gets its own package under `internal/`. Avoid cross-domain imports that would create cycles.

### 2. Interface boundaries at external edges

**Evidence:** `agent.LLM` and `agent.Runner` at `internal/agent/agent.go:110-145`. `RunStore` at `internal/db/memory.go:10-17`. `project.Store` at `internal/project/store.go:33-38`. `schedule.Repository` at `internal/schedule/store.go:47-54`. `planning.Store` at `internal/planning/types.go:97-115`.  
**Rule:** Persistence and external integrations use Go interfaces in the consuming package. This enables the memory/PostgreSQL dual-implementation pattern and test mocking.

### 3. Store/MemoryStore/DBStore persistence convention

**Evidence:** `internal/db/{memory,store}.go`, `internal/project/store.go`, `internal/schedule/store.go`, `internal/planning/{memory,db}.go`.  
**Rule:** New domain entities that need persistence provide both an in-memory implementation (for tests and fallback) and a PostgreSQL implementation (for production). The memory implementation uses `sync.RWMutex` and returns deep copies.

### 4. Embedded, lexically-sorted SQL migrations

**Evidence:** `internal/db/migrate.go:14-83`.  
**Rule:** Schema changes go in `internal/db/migrations/###_name.sql` files numbered in application order. Migrations are embedded and applied at startup. Never modify an applied migration; add a new one.

### 5. Parameterized SQL, no string concatenation

**Evidence:** All PostgreSQL stores use `$1, $2, ...` positional parameters.  
**Rule:** Never build SQL with string concatenation of user-supplied values. Use parameterized queries or `pgx` batch operations.

### 6. UUID primary keys with DB defaults

**Evidence:** Migration `001_init.sql` and all subsequent migrations use `uuid_generate_v4()` for PKs.  
**Rule:** UUIDs generated by the database (not application-invented sequential IDs) support distributed identity.

### 7. Diagnostic identifiers

**Evidence:** `isValidID` at `internal/api/server.go:111-122` provides a character-based traversal protection allowlist before database queries.  
**Rule:** Route parameters that become query values must pass type-appropriate validation before reaching stores.

### 8. Colocated Go tests

**Evidence:** `*_test.go` files in agent, api, auth, compare, events, gitdiff, intelligence, metrics, schedule, and visual packages. API tests use `httptest` with the memory stores.  
**Rule:** Unit tests live alongside the packages they test. Integration tests use the in-memory implementations.

### 9. Centralized frontend API client

**Evidence:** `frontend/src/lib/api.ts` is the single browser-side API contract.  
**Rule:** API calls in page components must go through typed functions in `api.ts`. Never scatter `fetch` calls across components.

### 10. `html/template` for generated HTML

**Evidence:** `internal/report/html.go:4-13,72-81`.  
**Rule:** Any server-generated HTML must use `html/template` with its contextual auto-escaping. Never use `text/template` or string concatenation for HTML output.

## Architecturally Recommended Principles

These are not yet established in the codebase but are recommended based on the architecture audit.

### 11. Separate transport from application logic

**Current gap:** Handlers in `internal/api/server.go` mix JSON decode, validation, business logic, store calls, event emission, and response encoding.  
**Recommendation:** Extract application services. Handlers own decode/encode. Services own transactions, business rules, and side effects.

### 12. One canonical execution path

**Current gap:** Five separate orchestration implementations with different state machines and semantics.  
**Recommendation:** Choose and enforce one orchestrator. Route all entry points (HTTP, MCP, schedules, webhooks, queues, approved cases) through it.

### 13. Explicit durable/ephemeral contracts

**Current gap:** Events, recordings, visuals, releases, notifications, reviews, suites, and sidecar jobs are always memory-backed.  
**Recommendation:** Every store must declare its durability semantics. Ephemeral stores must have bounded retention. Durable stores must have PostgreSQL backing.

### 14. Credentials as references, not values

**Current gap:** Project credentials and settings LLM API key are stored as plaintext in database columns and serialized in API responses.  
**Recommendation:** Store credential references (secret manager paths, encrypted tokens). Never return raw credentials in API responses.

### 15. Fail-closed security defaults

**Current gap:** API authentication bypasses when the key is empty; sidecar has no inbound authentication; CORS is wildcard.  
**Recommendation:** Every access boundary must default to denying access. Development-only bypasses must be explicit, configured, and logged.

### 16. Small files, single responsibility

**Current gap:** `internal/api/server.go` is ~3,556 lines combining routing, middleware, composition, 85+ handlers, and orchestration.  
**Recommendation:** Files should target <500 lines with one clear responsibility. Route modules, handler groups, and service packages are the established Go idiom.

## Anti-Patterns to Avoid

Based on verified audit findings:

1. **Don't add a new execution path as an inline handler.** Use the shared orchestrator (`ADR-001`).
2. **Don't add a new store without a memory implementation for tests.**
3. **Don't create database tables without a migration file in the numbered sequence.**
4. **Don't hard-code environment-like values** (timeouts, limits, URLs) that differ between development and production.
5. **Don't add dependencies without import evidence.**
6. **Don't mark a feature as complete in docs without verifying it against the active code path.**
